| 项 | 内容 |
| --- | --- |
| 来源 | Odoo 17.0 中文文档（公开站点），按**目录字母序**抓取 |
| 规模 | **40 页** · 合计 **139,967 字** · 单页中位 **2,569 字** |

## 二、复算方式（一条命令）

```
python tools/corpus_stats.py
SUMMARY pages=40 ops=25 apps=15 h2=125 h2_ops=80 h2_app=45 chars=139967
```

> 口径约定：「二级标题」= `toc.json` 中 `level == 2` 的条目；「运维 / 部署类」= slug 以 `administration` 开头。
> **数字与文档不一致时，以本脚本输出为准，并回写文档。**

## 三、结论

### 结论 1（成立）文档类型在抓取层面即可判别：40 页 = 25 运维 + 15 应用

**证据**：slug 前缀分布（`administration*` 25 页 / 其余 15 页）。
**用途**：F16.6.1「第 0 步」**可机判**——不必靠人逐份通读即可先分堆。

### 结论 2（成立）同一套抽取规则不能跨类型通用：两类文档的二级标题语义完全不同

**证据**（真实标题，各举 6 例）：

| 类 | 二级标题样例 |
| --- | --- |
| **运维 / 部署类**（80 个 h2） | 安装 · 版本 · 容器 · 子模块 · 更改托管解决方案 · 传输数据库 · 部署平台 · 升级概述 · 步骤 1：下载更新的 Odoo 版本 · 步骤 2：备份数据库 |
| **应用类**（45 个 h2） | 活动安排 · 所有已计划活动 · 活动类型 · 联系登记表 · 智能按钮 · 合并重复的联系人 · 删除重复联系人 |

**用途**：F16.6.1「**类型 → 可抽层**」映射表——用户手册可抽 K1 / **K2 功能** / K3 / K6；**运维 / 制度类禁止抽 K2**。

### 结论 3（证伪）「标题层级 = 功能模块树」不成立

**证据**：若按"二级标题 = 功能模块"直接抽，25 页运维文档的 **80 个二级标题**会被抽成 **80 个"功能模块"**，而它们实为「安装 / 版本 / 容器 / 部署 / 升级步骤」等**运维动作**。
**用途**：这正是「第 0 步：先判文档类型，再定可抽层」存在的理由；同时说明**标题层级位置不能作为抽取依据**。

### 结论 4（成立）层级深度不统一，抽取不能依赖"层级位置"

**证据**：h1 = **40**（与页面**一一对应**）· h2 = **125** · h3 = **246**（最多）· h4 = **79**——同一语义角色的标题在不同页面落在不同层级。
**用途**：抽取规则必须按「**文档类型 + 语义角色**」判定，不能按「层级位置」。

## 四、局限（须与结论同读）

| # | 局限 | 影响 |
| --- | --- | --- |
| 1 | **样本单一**：仅一方（开源 ERP）中文文档 40 页 | **不可外推**为"所有企业文档"的分布 |
| 2 | **分类依据是 URL 目录结构**（该站点自身目录清晰） | 真实企业文档多无此结构 → 企业侧「第 0 步」仍需人工或模型判型（故 F16.6.1 把类型判定列为**硬性前置**而非自动步骤） |
| 3 | **中文标题受翻译质量影响**（个别 h2 为整句，如"将图像的 WebP 版本用于…"） | 关键词统计会偏低，故本记录**不依赖关键词比例**下结论，而用**人工可读的标题样例**作证据 |
| 4 | 仅覆盖**文档结构**，不含「抽取准确率」 | 准确率需接入模型后另行实测（基线说明已列为已知未决项） |
