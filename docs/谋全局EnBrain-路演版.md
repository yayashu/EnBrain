# 谋全局 EnBrain · 路演版

> **数字纪律**：本文涉及人天、准确率等数值，一律标注性质（实测 / 设计目标 / 估算 / 待验证）；**未经核实的数字不写进结论**。

> **企业运营优化大脑 · 让企业的事实立起来，结论才有分量**
>
> **项目状态**：处于**需求与方案设计阶段**，**尚无产品化落地与真实项目交付**；文中能力表述均为设计口径与目标，实际形态以定稿、评审与实测为准。

## 概览（一页纸）

**我们要做的不是一次诊断，而是一座留在企业自己手里的事实底座**（需求与方案设计阶段）。

| 段落 | 结论 |
| --- | --- |
| **机会** | 企业在系统上的投入持续加码，但"这些投入买到了什么、还有哪些还在漏"始终拿不出一份能对账的答案——**判断一直靠人，事实一直散在几百份文档里** |
| **问题** | 卡住的不是判断力，是**事实从未被组织起来**：系统买了什么、买了有没有用、接口通了没通，散落各处，无人完整读过 |
| **定位** | **判断是服务，事实是资产**——不交付一份"更聪明的判断"，先建一份站得住的事实；事实一更新，结论即可重算 |
| **方案** | 一次诊断产出三类结果：**可对账的硬节省** · **可落地的机会** · **事实资产本体**（留在企业环境里） |
| **可信度** | 逐条可溯源 · 金额可独立复算 · 技术中立（主动给"不建议做 AI"的清单）· 抗幻觉三条硬约束 |
| **本次请求** | 2–3 家试点企业与其真实系统文档，用于**把"能省多少"变成客户自己算得出、复核得了的数字** |

**一句话可以拿去验证**：企业输掉一次维保或立项谈判，不是因为缺判断，而是**没人能把事实组织起来**。
## 1. 机会：投入在加码，判断仍然靠人

**过去十年，企业在系统上的投入是加法**：ERP、CRM、MES、OA 一套接一套，账面上有系统、有文档、有投入。但**"买到了什么、还有哪些还在漏"始终拿不出一份能对账的答案**——因为判断一直靠访谈、靠经验、靠汇报，而**事实一直散在几百份文档里，从未有人完整读过**。

**这个问题在今天具备被解决的条件，原因是三件事同时成熟**：

- **文档化程度已到位**：企业自有的系统文档、流程说明、接口约定、运维手册，客观上已经存在——**这是唯一不需要企业额外付出的事实来源**。
- **长文档结构化已可用**：把成套文档读成逐条可溯源的结构化事实，过去是人工工程，现在是可交付能力。
- **企业与顾问的关系已改变**：企业真正愿意长期复用的，不再是"更聪明的判断"——**判断随人走、随行业变**，换个顾问换个年份结论就变；能自己复算的事实底座才是留得下来的东西。

**判断**：机会不在"AI 提效"，而在**企业第一次有机会拥有自己可核验的事实**。这个位置此前没有产品占住。

## 2. 问题：三个角色，同一种无力感

| 角色 | 他们真正卡在哪 | 现有方式为什么接不住 |
| --- | --- | --- |
| **CEO / 总经理** | 知道要降本增效，说不清"哪几个环节最该动"；怕投入打水漂 | 咨询给结论不给依据，数字无法复核 |
| **CIO / 数字化负责人** | 讲不清优先级、拿不出立项依据，无法向老板量化收益 | 看板回答"这个数是多少"，回答不了"这个数怎么来的" |
| **业务负责人** | 自己流程哪里能优化、改了之后人怎么办，没人告诉他 | 通用 AI 助手解决个人提效，不解决系统性优化 |

**共同点不是判断力不够，而是事实没有被组织起来。** 具体表现为四个可观察的漏损：**买完就闲置的系统**、**上线后从未被打开的功能**、**跨系统之间靠人搬的数据**、**说不清自己买了什么的资产台账**——这些漏损每天都在发生，但没人能拿出一份**逐条可对账**的清单。

**因此问题不在"要不要用 AI"，而在"凭什么判断"**——凭人说的，还是凭白纸黑字、可核对、可复算的事实。

**判断**：这一节确立了项目的立足点：**先解决依据问题，再谈方法优劣**。
## 3. 定位：判断是服务，事实是资产

**企业真正缺的不是更聪明的判断，而是一份站得住的事实。** 判断会过时，事实不会——**判断是服务，事实是资产**。

所以本产品的做法与本类项目相反：**不交付一份更聪明的判断，而是先用企业自有文档建一份站得住的事实底座，再让结论从事实里长出来。** 三条推论决定了产品形态：

1. **输入只有企业文档**——企业自行导出后上传，**不装任何东西进企业系统、不直连业务系统**；这既是交付轻量的前提，也是信任的前提。
2. **结论必须能复算**——每条结论都能定位到文档的具体位置，"这个数怎么来的"必答；**客户拿计算器就能独立复核**。
3. **事实一更新，结论即可重算**——系统升级、组织调整之后**不必重做诊断**，更新事实、重跑落差即可。**这决定了产品的长期价值形态：不是一份会过时的报告，而是一项会增值的资产。**

**判断**：按这个定位，产品的竞争力不来自模型能力，而来自**企业自己手里那份可复算的事实**——**这既是差异，也是壁垒**（第 8 章展开）。

## 4. 方案：一次诊断，三类交付

**方案设计的机制链条**（全程可溯源，末端可复算）：

```
企业文档（唯一输入）
   → 结构化事实（六类：系统 / 功能 / 流程 / 数据结构 / 集成 / 规则，逐条可溯源）
   → 层间落差识别（"应有" vs "实际"，逐条比对）
   → 一次诊断产出两类结论 + 一份资产本体
   → 报告四模式交付 + 执行档案 → 闭环回填
```

| 产出 | 内容 | 为什么它成立 |
| --- | --- | --- |
| **① 可对账的硬节省** | **硬三类**——闲置系统、未启用功能、手工搬运；每条对账到金额 | 设计上要求**客户拿自己的合同与台账即可独立复核**，不依赖客户相信我们 |
| **② 可落地的机会** | 带依据、带优先级的候选机会；业务部门**三态拍板**（成立并落地 / 方案需调整 / 不成立 + 结构化理由） | 把判断权交回业务，**不替客户做决定** |
| **③ 资产本体** | **全量事实底座**，逐条可溯源，**留在企业环境里**（本地化部署） | 结论会旧，**事实只增不减** |

**同一批事实，四种读法——这是"一次投入、多次受益"的关键**：日常查询（这项功能到底有没有人用）· 变更影响分析（改这个接口会影响谁）· 交接与合规输出（系统怎么解释自己）· **维保与验收对账**（合同有没有被履行、该续约还是该调整）。

**交付出口：报告四模式**——专业版（CIO 逐条核对）· 人话版（业务与员工看懂）· 汇报版（CEO / 董事会，一页纸）· 合规应答版。**同一批结论，四种读者，不重写事实。**

**判断**：这一章回答了"卖什么"——**卖的是一次可复算的诊断，加一项可长期使用的资产**。
## 5. 凭什么：五条设计约束（尚待实测验证）

1. **事实优先——交付的不是结论，是资产**（设计约束：结论只作事实的读数，不作最终交付物）**。** 结论只是事实的读数；系统升级、组织调整后不必重做诊断，更新事实、重跑落差即可。
2. **逐条可溯源，金额可独立复算。** 每条结论能定位到文档的具体位置；"这个数怎么来的"必答。
3. **技术中立，不为 AI 而 AI。** 规则明确的环节直接回答"用系统配置或自动化就够了，别花 AI 的钱"——**我们主动给出一份"不建议做 AI 的清单"**。
4. **抗幻觉三条硬约束。** 根因**只从封闭集合里选**（禁止自由生成）· 证据**必须能程序化映射**到事实字段 · 置信度**由规则计算**，不由模型打分；低置信结论**必须经用户确认**才进入关键结论。
5. **同引擎双覆盖。** AI 也是企业资产的一类——与系统资产同一张台账、同一套落差识别，**不建第二张台账、不另立报告章节**。

### 竞品一眼看清

| | 咨询公司 | 通用 AI 助手 | 数据看板 | **谋全局 EnBrain** |
| --- | --- | --- | --- | --- |
| 事实来源 | 访谈 + 顾问经验 | 公开语料 | 企业业务数据 | **企业自有文档（全量 · 可溯源）** |
| 结论可复算 | 难 | 不可 | 数字可，口径难 | **是（层间落差可复算）** |
| 资产是否留在企业 | 否 | 否 | 数据在、方法不在 | **是（本地化部署，事实留企业环境）** |
| 技术中立 | 有（人判断） | 无 | 不涉及 | **有（含"不建议做 AI"清单）** |
| 事实一变怎么办 | 重做 | 无关 | 看新的数 | **重跑落差即可** |
| 谁承担判断责任 | 顾问 | 用户 | — | **业务部门三态拍板** |

**判断**：五条里最容易被模仿的是"用 AI 做分析"，最难被模仿的是第 2 条与第 4 条——**可复算 + 封闭集合约束**，它们约束的是产品敢承诺什么，而不是模型有多强。

## 6. 产品形态与交付方式

| 维度 | 本期口径 |
| --- | --- |
| **交付形态（拟定）** | **本地化 / 私有化部署，服务单企业**（SaaS 为架构预留，**非本期形态**） |
| **能力结构** | **主线**（事实引擎 · 诊断引擎 · 流程优化 · 机会闭环 · 履约核查 · 报告交付 · 员工知识助手）· **支撑**（画像补全与实时共建 · 权限与安全）· **扩展**（知识与协作面）。**主次是依赖关系不是优先级**：支撑缺了主线停摆，扩展缺了只是少用 |
| **起效路径** | 文档就绪度评估表判断能否接单 → **六步一次跑完** → 报告四模式 + 执行档案 → 闭环回填 |
| **人工投入** | 人工集中在**事实确认与业务拍板**环节，其余由系统完成；**具体量级待首个真实项目校准**（本文不给未经验证的数字） |
| **数据信任** | 本地部署 · **隔离红线**（不直连业务系统 · 不用于训练 · 可导出可删除 · append-only 审计日志）· 隐私红线（问答只记频次不记内容 · 盲区不展示提问人 · 不用于绩效） |

**判断**：这一章最关键的一条仍是**"不直连业务系统"**——它同时决定了交付成本、信任成本与合规成本，**是这个产品能规模化交付的前提，而不是能力缺失**。
## 7. 市场与进入策略

**先筛客户，再谈打法。** 四道硬门槛不达标就不接单：

| 门槛 | 为什么是门槛 |
| --- | --- |
| 系统数量多到人工难盘清 | 事实底座的价值随系统复杂度上升，零散系统做不出差异 |
| 系统文档可获取 | **文档是唯一输入**，拿不到文档就没有事实来源 |
| 有 IT 对接人 | 交付靠一次集中的事实确认，不靠远程猜测 |
| 有明确的成本或漏损压力 | 没有压力就没有改变的动力 |

**获客：用可验证的交付物换信任，而不是用 AI 讲故事。** 第一份交付物是**客户自己算得出、复核得了的数字**——这比任何演示都有说服力。

**转化：靠第一次的结果决定客户会不会继续用**——不靠试用路径，靠"客户自己算出的数字站不站得住"。试点解决"能不能看见"，结果决定后面还有没有第二次。

**留存与扩展：靠"常驻监控 + 事件响应"让客户持续用下去。** 事实底座常驻，接口变更、系统上线、组织调整时触发重算与提醒——**客户留下来的不是一套工具，是一份持续更新的事实。**

**判断**：这套打法与"先立事实"的定位互为因果——**没有可验证的第一份交付物，就进不了门；没有持续更新的事实，就留不住**。

## 8. 竞争与壁垒

**竞争分两层看**：同层是"企业优化诊断"（咨询与体检服务），上层是"通用 AI 与数据看板"——**同层拼顾问经验，上层拼数据接入**；EnBrain 的位置在两者之间：**不拼经验，也不拼接入，拼"企业自有文档 + 可复算结论"**。

| 壁垒 | 为什么构成壁垒 | 强度 |
| --- | --- | --- |
| **企业自持的事实资产** | 事实底座一旦留在客户环境并持续更新，**更换服务方等于重建全部依据** | 高（随时间累积） |
| **可复算的方法与封闭集合约束** | 逐条溯源与根因封闭集合是工程约束，不是提示词技巧，**难以靠通用模型快速追平** | 中高 |
| **交付动作的资产化** | 一次诊断沉淀为可复用的解析与识别资产，**边际交付成本随客户数量下降** | 中（需真实项目验证） |
| **不锁定厂商与平台** | 客户不被单一技术栈绑定，**这本身就是采购决策中的加分项** | 中（是选择权，不是壁垒） |

**诚实说明**：截至目前**壁垒的"高"只成立于"客户已跑完并持续使用"之后**；在试点阶段，壁垒接近于零——**所以第 11 章的验证顺序比本章的结论更重要**。

**判断**：这个产品的护城河不是技术，是**时间与客户自有资产**；因此打法必须从"跑通第一家并让它持续用"开始，而不是从铺量开始。

## 9. 里程碑与验证顺序

**验证按步骤推进**——每一步只证明一件事，证明不了就停在那一步：

| 步骤 | 要证明的 | 通过判据 |
| --- | --- | --- |
| 一、试点接单 | 文档能读成结构化事实 | 文档就绪度评估通过；事实抽样可溯源 |
| 二、一次诊断 | 硬三类金额客户能自己算出来 | 客户复核通过，无争议项 |
| 三、结论落地 | 机会被业务部门三态拍板 | 至少一项进入"成立并落地"并回填实测 |
| 四、持续使用 | 事实更新后结论重算有价值 | 客户认可常驻监控与事件响应，并把它用进日常 |
| 五、规模化 | 交付边际成本下降 | 同一交付动作在第二家客户的复用率可量化 |

**四个当前未决项（对外如实标注）**：真实企业文档实测表现 · 抽取准确率（模型能力类指标只给目标值与校准机制）· 交付人力能否随客户数量摊薄 · AI 供应商评测。**凡涉及人天 / 准确率的数字，均为设计目标或估算，不得表述为实测值。**

**判断**：**先做一次可复算的诊断，再谈规模化**——这个顺序错不得，否则后面每一步都建在未验证的假设上。

## 10. 风险与对策

| 风险 | 性质 | 对策 |
| --- | --- | --- |
| **客户文档质量不可控**（扫描件、过版、缺章） | 交付前可见 | 文档就绪度评估表设接单门槛；不足则降级为方向性结论并明示 |
| **抽取准确率不达标** | 模型能力类，取决于客户语料 | 只承诺"可核验的交付形态"（逐条可溯源 / 金额可对账 / 报告可整份导出 / 达不到时降级明示），**不承诺模型分数** |
| **交付人力成为瓶颈** | 运营类 | 解析与识别沉淀为可复用资产；同一交付动作跨客户复用率纳入跟踪 |
| **隐私与合规风险** | 不可控风险 | 本地部署 · 隔离红线 · 不用于训练 · append-only 审计；**风险不可控的能力不做** |
| **技术供应商依赖** | 战略类 | 技术中立、不锁定模型厂商，模型层可替换；关键结论的约束落在系统而非模型 |
| **AI 结论被当作行政或管理决定** | 合规类 | 产品只回答"这个数怎么来的"；落地判断由业务部门三态拍板，系统不代替决策 |

**判断**：这套对策的共同取向是**不承诺不可控的东西**——这也是为什么第 5 章只敢承诺四条与行业无关、可由系统与流程保证的交付属性。
## 11. 本次决策请求

**我们要的**：2–3 家**首批共建企业**的对接与**真实系统文档**，用于把"能省多少"从估算变成**客户自己算得出、复核得了的数字**。

**我们要一起验证的三件事**：

1. **可复算性**——硬三类金额能否被客户独立复核，有无争议项；
2. **可落地性**——机会能否被业务部门真实拍板并回填实测结果；
3. **可持续使用**——事实底座常驻后，客户是否认为"持续看得见"值得一直用下去。

**继续投入的判据**：若第一次试点证明"客户算出的硬节省"显著大于一次诊断的人力成本，且机会进入落地闭环，则进入第二步验证；若不成立，则收敛为"一次性体检服务"，不再投入常驻产品化。**这个判据在启动前就写定，避免事后改口径。**

## 结语

> 让每一家企业，无论大小，都**先把自己的事实立起来**——然后每一个"该改什么"，都能被自己复算一遍。
>
> 这就是——**谋全局**。
